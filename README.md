# VVE Tasks API

ASP.NET Core Minimal API. Создание, просмотр, завершение и удаление задач. При завершении задачи публикуется событие в RabbitMQ.

## Технологии

- .NET 9, ASP.NET Core Minimal API
- PostgreSQL 17, EF Core 9, Npgsql
- RabbitMQ 4, RabbitMQ.Client 7
- Swagger UI
- xUnit, WebApplicationFactory
- Docker Compose

## Быстрый запуск

Для запуска нужны Docker и Docker Compose
Перейти в каталог с `VVE.slnx` и `docker-compose.yml`:
```powershell
docker compose up -d --build
```

Compose запускает PostgreSQL и RabbitMQ, дожидается их готовности и запускает API. Перед запуском HTTP-сервера приложение автоматически применяет миграции EF Core.

## Проверка API через Swagger

Открыть http://localhost:8080/swagger.

1. Создать задачу через `POST /tasks`.
2. Скопировать `id` из ответа.
3. Проверить список через `GET /tasks`.
4. Завершить задачу через `PUT /tasks/{id}/complete`.
5. Повторить завершение — ожидается `409 Conflict`.
6. Удалить задачу через `DELETE /tasks/{id}`.

Swagger и OpenAPI доступны в окружении `Development`, которое используется в Compose.

## Основные ошибки:

- `400 Bad Request` — некорректные данные, JSON, идентификатор или приоритет.
- `404 Not Found` — задача не найдена.
- `409 Conflict` — задача уже завершена либо изменена или удалена другим запросом.

### Разделение ответственности

- **Domain** — сущность задачи и доменные правила.
- **Application** — сценарии использования, команды, запросы и контракты инфраструктуры.
- **Infrastructure** — EF Core, PostgreSQL и публикация в RabbitMQ.
- **API** — HTTP-маршруты, DI, обработка ошибок и Swagger.
- **Tests** — проверки HTTP-сценариев, конкурентности и публикации событий.

Используется упрощённый CQRS, запросы получают данные через read-репозиторий с `AsNoTracking()`, команды работают с отслеживаемыми сущностями и сохраняют изменения через `IUnitOfWork`.
`TaskDbContext` реализует `IUnitOfWork`. В пределах одного HTTP-запроса репозитории и Unit of Work используют один экземпляр контекста.

## RabbitMQ

Пример сообщения:

```json
{
  "taskId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "title": "Купить молоко",
  "completedAt": "2026-10-15T12:00:00+00:00",
  "priority": "High"
}
```

Порядок действий:

1. Завершение доменной сущности.
2. Сохранение изменений в PostgreSQL.
3. Помещение события в ограниченную очередь в памяти.
4. Асинхронная публикация фоновым сервисом.

Одним RabbitMQ-каналом пользуется один фоновый обработчик.

При ошибке подключения или отправки задача остаётся завершённой, а полное событие записывается в лог. При переполнении очереди событие также логируется. Следующее событие вызывает новую попытку подключения.

Успешный вызов публикации логируется на уровне `Information` с типом события и JSON сообщения.


## Принятые упрощения

- Нет пагинации, фильтрации, сортировки и аутентификации.
- Нет consumer в приложении.
- Нет outbox и автоматического повторного отправления событий из лога.
- Очередь публикации находится в памяти, поэтому аварийное завершение процесса может привести к потере событий.
- Publisher confirms не используются: успешный вызов публикации не является подтверждением сохранения сообщения брокером.
- Учётные данные в Compose предназначены для локального тестирования.
